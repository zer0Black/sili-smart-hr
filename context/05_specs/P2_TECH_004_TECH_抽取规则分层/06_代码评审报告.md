## 一、必修（阻断级）

### 1. RetryDelayFunc 负移位 panic，任一任务首次失败击穿整个进程

- 位置：`hr-backend/internal/worker/server/server.go:27`
- 置信度：CONFIRMED（已读 asynq v0.26.0 源码核实调用契约）

```go
d := retryDelayBase << (n - 1) // 30s/60s/120s，超出按封顶
```

asynq v0.26.0 `processor.go:358` 以**自增前**的 `msg.Retried` 调用 RetryDelayFunc，任务首次失败重试时 n=0，`30s << -1` 触发 `runtime error: negative shift amount`。关键在于 panic 落点：`p.retry` 在 exec 循环的 worker goroutine 内执行，位于 `perform()` 的 recover 保护之外（recover 只包 handler 调用层，processor.go:426），未恢复的 goroutine panic 直接杀死整个单进程二进制（HTTP server + worker + scheduler 同时死）。

触发条件极低：session-extract 首次遇到网络抖动、5xx、或本变更集自己新增的 550s 超时返回 ctx 错误，走默认重试分支即爆。当前生产仅 health:check（恒 nil）入队所以潜伏，pipeline 入队落地即爆雷。

附带变体（同一行代码）：任务级 MaxRetry ≥ 35 时 `30s << 34` 溢出为负 Duration，负值绕过 `d > retryDelayCap` 封顶检查返回负数，任务被立即重试形成热循环打满 Redis。

修复建议：n ≤ 0 钳到 1，先封指数再移位；补一个表驱动单测覆盖 n=0/1/34/35。

## 二、正确性缺陷

### 2. 探测计分先于 transcript 重放剥离，client 列可被重放噪音污染

- 位置：`hr-backend/internal/engine/extractor/classify.go:478`
- 置信度：CONFIRMED（代码路径确认；真实数据抽查样本未触达重放形态）

消息循环内 `detect.score(detectPlans, m)` 在 479 行 transcript 开闭标签判定与 491 行 replayDepth 剥离**之前**执行。被分类侧显式判为不可信并整块丢弃的重放载荷，仍参与客户端探测计分：claude_code 会话重放含其他客户端签名的旧会话（如 `# Environment`、`TodoWrite ` 打头行，权重 2-3），边缘会话裁决被推向 mixed 或错归属。session_features.client 随行固化且 success 行终态不重判，污染不可逆，而 client 维度观测（skip_ratio 按客户端拆分）正是本 feature 的核心交付。

顺带浪费：重放载荷可内嵌整个历史会话，每条消息都跑 14 个特征的 strings.Contains 计分后才被丢弃。

修复建议：score 移到 replayDepth 判定之后（与 tool 行跳过同位）；`DetectClient` 独立入口同步同口径并更新等价性断言。

### 3. fetch 失败路径复用 legacy 空串 client，破坏自设的观测桶分离

- 位置：`hr-backend/internal/engine/extractor/extract.go:302`
- 置信度：CONFIRMED

确定性拉取失败（ErrUnauthorized 等）路径复用既有行 client 原值。存量库的 legacy 失败行（client 列迁移兜底 DEFAULT ''）重抽再失败时，`meta.client=''` 被原样落回，与代码注释宣称的「防 fetch 错误行混入 detail_invalid 观测桶」相反——它们又回到了 '' 桶。子情形：`rowMetaOf` 的 FindBySessionKey 瞬时失败被吞错返回 nil 时，pc.client 保持 unknown，会覆盖既有行的真实 client（如 omo → unknown）。

影响限于升级前已有 failed 行的存量库，下次成功重抽自愈，严重度中低。修复建议：`meta.client` 为空串时保持 unknown。

## 三、存量库迁移问题

### 4. inject_prefixes 语义翻转（替换→追加）无存量数据迁移

- 位置：`hr-backend/internal/model/migrate.go:77`
- 置信度：CONFIRMED

seed 改为空数组但 `FirstOrCreate` 行存在即跳过：从旧版升级的部署 system_params 仍存 59 条旧出厂全集 JSON，且行内描述还是替换语义的旧文案。当前并集去重后行为恰好等价（不炸），但：

- 旧库运维在替换语义下做过的前缀删除（当时合法的放开手段）被静默撤销，出厂并集恒生效且参数页无法再收回；误杀的 user 消息可致会话不可逆落 empty_shell
- 运维在参数页看到 59 条来历不明的「追加条目」，无法区分哪些是自己加的
- 未来下线某个出厂前缀时，存量库旧全集作为追加集让它永远拦着，新旧库行为分叉且无测试可见

建议：对存量行做一次性清空迁移（识别旧出厂全集值），至少在升级说明中披露语义变化。

### 5. 01 规格书与存量迁移钩子口径漂移

- 位置：`hr-backend/internal/model/migrate.go:118`（钩子本身）与 `01_功能需求规格说明书.md` §1.4/§4.3
- 置信度：CONFIRMED

钩子工程上是对的（有数据行的库 NOT NULL 无 default 加列会被 SQLite/PG 拒绝，DEFAULT '' 兜底，三方言兼容，有回归测试）。但 01 规格书仍写着「新项目无历史库，不做存量迁移」，与本变更集新增的 migrateSessionFeatureClient 形成双口径，同 diff 只修订了 04。后续会话若以 01（自称唯一权威）为准删掉钩子，跑过 TECH_003 的存量库升级即启动失败且难定位。建议补 01 的 7.4 变更记录条目并修订 §4.3 表述。

## 四、质量项

### 6. 550s 任务超时零冗余，推导链散落三文件

`hr-backend/internal/worker/task/health.go:24`：550s = 190s 拉取退避 + 360s LLM 双调用，严丝合缝无余量。最坏会话在 persistSuccess 落库阶段被 deadline 取消，每次重试重烧满 550s，MaxRetry=25 内永不落行且持续占用并发额度。预算只存在于 providers.go 注释里，worker 侧常量与其无任何编译期/测试期关联，后续调参（MaxRetries 或 Timeout 上调）即静默失配。建议给落库留冗余（如 600s）或单点声明推导链。

### 7. 8 处 doc 注释违反注释密度约束

CLAUDE.md 明文「函数 doc 注释不超过 4 行、同一函数 specs 引用最多 1 处」。违规：config.go InjectPrefixes（6 行）/ appendEffectivePrefixes（6 行 3 处引用）、classify.go classifySequence（8 行 4 处引用）、health.go NewMux（6 行沿革复述）、detect.go DetectClient（5 行 2 处引用）、extract.go llmExtract（5 行 2 处引用）、system_param.go fallback（6 行矩阵罗列）、trim.go buildView（6 行且 specs §6.1 重复两处）。建议按约束精简。

### 8. 测试基建多源重复

`rules/registry_test.go:144` 等：59+4 条前缀基线快照在 rules 与 extractor 两包各硬编码一份（注释自称同源），配套 diff helper 逐行相同抄两份；注册表 fake 三份变体（detectFakeClient / newClientFake / fakeClient）；500 消息性能语料两套独立构造加永不判失败的计时观测线。增删一个前缀要同步改两份清单多处锚定，漏改即等集断言互相矛盾。建议快照单源化（rules 包导出测试取值函数）、语料与 fake 收敛。

### 9. 注册表无锁，测试期 Register 有竞态隐患

`rules/registry.go:45`：allRules 无锁包级切片，契约是 init 期单 goroutine 写入，但 registry_test / detect_test / rules_layering_test 均在测试运行期 Register。当前全仓无 t.Parallel 侥幸成立；任何人给触碰注册表的测试加 t.Parallel 即构成数据竞态。可加 sync.RWMutex 或在契约注释明示禁并行。
