## 本次需求澄清关键决策

以下决策在愿景文档基础上明确，后续模块与 PRD 须遵循（1 至 5 为首轮澄清，6 至 13 为模块生成后经用户确认的补充决策，14 至 18 为原型对齐后补充的决策）：

1. **需求澄清覆盖完整范围，范围裁剪留待 PRD**。本次澄清完整覆盖使用活跃度、AI 使用能力（底层 4 维 + 上层 4 维）、通用素质全部 8 项，保留能力模型的完整性。MVP 实际做哪些模块、性格/胜任力/价值观是否纳入首期，属于范围裁剪决策，由产品在 PRD 阶段定夺，需求澄清阶段不做此项决策。
2. **组织规模定位于中型**。首期部署覆盖全公司 100 至 500 人，批处理与 LLM 调用成本纳入约束，但尚未达到需要重型架构治理的量级。
3. **员工本人不是平台用户**。平台账号不区分角色、统一全权，员工无平台主入口，看不到画像与评分理由。此为相对愿景文档第 6、9 节原设定的重要变更。主动测试作答另经一次性轻量作答页落地，见决策 6。
4. **首期不引入组织架构**。复用 sili-smart-api 的用户信息，仅取 user_id 到人名的映射。部门归属、按团队划分可见范围、按部门钻取全部后置。团队看板首期做全公司整体聚合。
5. **新增 AI 管理能力作为高阶维度**。参考领导力胜任力方法论迁移到管理 AI 的场景，含目标对齐、授权分工、监督验收、风险担责、人机协作 5 个子能力，数据来源限定为主动测试场景题，与对话分析的上层 4 维物理隔离以避免重复计分。首期主动测试产品化为 AI 管理能力场景题与九型人格两个测评。
6. **员工作答经一次性轻量作答页**。主动测试需要员工本人作答，落地方式为系统生成一次性作答链接，经 IM 或邮件推送，员工进入轻量作答页提交作答后链接即失效。作答页仅承载作答提交，不提供画像、看板、评分理由的浏览能力。此为对决策 3 的细化：员工没有平台主入口，仅有一个用于提交测试作答的一次性入口，决策 3 所述看不到画像与评分理由不受影响。
7. **平台不设角色权限模型，账号统一全权**。所有平台账号登录后拥有相同功能，不做角色划分与权限分配。这与首期无组织架构（决策 4）一致：无组织架构时无法按团队划分可见范围，故看板继续做全公司整体聚合，所有账号可见全员画像，待组织架构对接后再考虑可见范围收敛。
8. **评估周期可配置，默认一周一次，周日 23 点后跑本周全部**。周期批量跑批的周期长度由 HR 在后台配置，默认值为一周，触发时点默认为周日 23 点之后，跑批对象为本周累计的全部会话数据。默认周频意味着 LLM 调用量与成本明显高于月度方案，成本预算、队列节流与跑批时长估算需按周频核算，一个活跃员工一周可能产生数十个会话，全公司周跑批调用量可观。
9. **平台账号不细分运营角色**。不区分所谓管理员与普通使用者，也不引入独立的系统管理员或技术运维角色。平台账号统一拥有配置维护、评估运营、结果消费、异常处置的全部功能；大模型配置、跑批节流、告警处置等技术运维性质的工作由平台账号承担，不再单设角色。
10. **九型人格改用标准量表，AI 只做型别判定**。九型人格放弃 LLM 动态生成情境题的方案，改为引入经过验证的标准九型量表作为固定题库。AI 的职责收敛为基于作答结果判定主型、翼型与 9 型倾向分布，不再出题。原因：九型实证基础本就偏弱，标准量表的信效度远高于 LLM 即兴生成，用更不可靠的方式做本来就弱的事不合理。具体量表选型与授权方式留 PRD。
11. **题库审核改为 HR 统一批量标记驳回制**。题库不再逐题审核。HR 进入统一审核界面，对一批题目过目，只对不合适的单个题目做标记，被标记的驳回、未标记的默认通过入库。机制对 AI 管理能力生成题与九型标准量表题统一适用，但按来源分批审核、不在同一批次混审，审核焦点不同：生成题审场景质量与偏见，标准量表题审本公司适用性。
12. **主动测试运营为单次定向发起，"一次性"指作答链接而非作答次数**。主动测试由 HR 按需对特定人员单次定向发起，每次生成一次性作答链接推送，员工提交后失效。员工作答可由 HR 按需多次发起，"一次性"修饰的是链接与作答页会话的单次有效，不是作答总次数。

13. **评估运营三页收敛为评测运营中心一页**。原跑批记录与监控、手动定向分析、主动测试追踪三页合并为评测运营中心（assessment-batch-list.html）。手动定向分析降级为发起评测弹窗里的对话分析入口，主动测试追踪并入统一记录的 AI 管理能力与九型 tab。页面按 HR 动作（监控、发起、查记录）组织，不再按数据来源切分。跑批失败兜底暂不纳入本页，定时跑批配置仍保留在系统参数页，评测中心只读展示下次跑批计划。业务功能本身（周期批量、手动定向、主动测试追踪）不变，仅承载页面收敛。

14. **大模型配置页统一承载对外对接密钥**。大模型配置页（secret-config.html）除维护 LLM 模型清单与排他启用外，增设sili-smart-ap日志集成密钥的维护项。sili-smart-ap日志集成密钥是平台访问 sili-smart-api 对话日志的 Bearer 鉴权凭据（环境变量 CONVERSATION_LOG_INTEGRATION_KEY），与 LLM 的 API Key 同属平台对外系统的对接密钥，合并到该页统一脱敏展示、轮换与连通验证，不再单设独立的集成密钥页。此决策补齐数据命脉鉴权凭据此前无处维护的缺口。

15. **不设站内通知中心，告警与提醒融入业务页面**。平台不建独立的站内通知中心页面，亦不在顶栏设通知铃铛入口。跑批失败比例超阈告警以工作台首页的待处理指标与评测运营中心的统计卡呈现，主动测试逾期以评测运营中心对应记录行高亮与重发操作呈现；员工侧的作答提醒不进站内，经 IM 或邮件外发。运营人员长期驻留工作台与评测中心，告警就近融入消费页比独立通知中心更直接；员工本就无平台入口，提醒只能外发。

16. **跑批失败兜底首期以后端自动处置为主，不单设失败列表页**。失败兜底逻辑（自动重试、重试耗尽降级保留统计、失败比例超阈告警）保留，但首期不设独立的失败会话列表或补跑页面：重试与降级由评估引擎自动执行，失败比例超阈在工作台告警卡体现，需要补齐时由运营在评测运营中心的发起评测弹窗里以对话分析类型选定对象与时段触发定向评估作为补跑，不单设补跑入口。此为对决策 13 将兜底移出评测运营中心后的归属补充，补跑复用手动定向分析入口。

17. **AI 管理能力题为情境题，选项以自然文本写在作答要求中**。AI 管理能力题每题含情境简述与作答要求，作答要求中以自然文本给出若干选项（如 A/B/C/D），不单独建立选项数据结构、不预设标准答案、不做题型枚举分类（去题型组合）；员工作答通过与 AI 逐题对话，可说明所选选项与理由并补充，AI 结合对话过程阅卷。九型人格为 Likert 量表数字作答。此口径统一既有共识与原型实现：选项作为作答要求的自然文本存在，但不结构化为题型字段，亦无题型枚举。


## 业务需求分析

### 一、业务性质与模式

sili-smart-hr 是面向企业内部的综合人才测评平台，用 AI 完成对人员多维度能力的评估。其定位要点：

1. 所属领域为人力资源数字化中的能力测评与人才发展细分领域
2. 定位为内部系统能力，而非外部售卖的 SaaS 产品
3. 价值通过提升团队 AI 使用水平、识别短板人群、指导针对性培训来体现

在数据价值链上，sili-smart-hr 处于兄弟系统 sili-smart-api（基于 new-api 的 LLM 网关）的下游，是数据消费方：

1. 把 sili-smart-api 沉淀的员工 AI 对话日志转化为能力评估信号，再叠加主动测试，形成个人与团队的人才画像
2. 两者松耦合：sili-smart-hr 通过集成密钥 Bearer 调用 sili-smart-api 的会话日志接口，LLM 评分与阅卷走平台在大模型配置页自配的模型，模型地址与密钥由运营人员维护，可指向 sili-smart-api 网关也可直连其他模型

核心差异化在 AI 使用能力评估：

1. 市面通用测评工具无法分析员工的 AI 使用水平，因为只有 sili-smart-api 的对话日志能提供这个数据源
2. 这项独有资产决定了 sili-smart-hr 的竞争位势无法被通用工具替代

### 二、核心资源与能力

系统运作依赖三类关键资源，归属与控制模式各不相同。

**第一类：对话日志数据资产**（归属 sili-smart-api）

1. 存储于 ClickHouse 日志库
2. 是 AI 使用能力（底层 4 维 + 上层 4 维）评分的信号来源
3. 通过 session_key 组织会话，以 request_id 为业务标识（表中 id 恒为 0，不可用作业务键）
4. 采用增量存储：首轮存全量、后续轮存增量，分析时必须用详情接口把完整 messages 拼回
5. 工具可见度有限，通常只记录是否使用工具及调用次数，工具定义、调用参数和 system prompt 是否留存需在架构设计阶段核实
6. 访问通道是 `/api/conversation-log` 接口，认证用环境变量 `CONVERSATION_LOG_INTEGRATION_KEY` 的集成密钥 Bearer

**第二类：LLM 调用能力**（平台自配模型承载）

1. 底层维度的全量 LLM-as-judge 评分、AI 管理能力题生成与阅卷统一走平台在大模型配置页排他启用的模型（OpenAI 兼容的 `/v1` 调用）
2. 模型的服务商、模型标识、API 地址与密钥由运营人员维护，可指向 sili-smart-api 网关，也可直连其他模型服务商；同一时刻仅一个模型启用，平台所有 AI 能力统一调用该模型
3. LLM-as-judge 是评分质量与一致性最高的手段

**第三类：sili-smart-hr 自有资产**（存于 PostgreSQL）

1. 包括评分记录、个人画像、团队看板数据、维度与权重配置、题库、主动测试记录
2. 所有权与控制权完全在 sili-smart-hr 侧

工程上还有一个待建的核心能力：通用评估引擎底座。

1. 职责是出题、LLM 阅卷、多维打分、聚合、报告生成，所有维度模块共享
2. 底座搭好后，新增维度等同于填内容，这是支撑范围扩展的关键架构前提

被测评对象与平台用户：

1. 被测评对象为首期全公司 100 至 500 名员工，作为评估数据来源与画像主体，不是平台用户，无任何系统入口
2. 平台账号不区分角色，登录即拥有全部功能；账号由运营在用户管理页维护（账号、姓名、密码、启停、最近登录），登录校验基于本台账（决策 18）
3. 人员信息复用 sili-smart-api 的用户体系，首期只取人名，组织架构对接延后

### 三、关键业务流程与场景识别

评估由一条基线层和两条主线构成，各自的数据来源与触发方式不同。

**基线层：使用活跃度**

1. 性质是纯规则统计，不调 LLM
2. 从 conversation_turns 的 user_id、created_at、session_key 统计
3. 产出指标包括近期会话数、轮次数、最近一次使用时间、使用趋势
4. 回答这个人用没用 AI、用得多频繁
5. 分级为活跃、低频、未使用，未使用判定为本跑批周期内 0 轮对话。活跃度统计与 AI 使用能力跑批同周期进行，统计范围即跑批周期，周期长度在系统参数页配置；活跃与低频的分级轮次阈值在维度与权重页的活跃度配置维护
6. 活跃度独立于两大能力模块，是能力评分的前提：一个未使用用户没有对话数据，能力维度无从评分，画像以活跃度为主；对话数据不足时能力维度降权

**主线一：对话分析**（覆盖 AI 使用能力全部 8 维，即底层 4 维 + 上层 4 维，是核心评估通道）

评估能力的依据是用户在对话中体现的行为模式，不是工具调用的字面归属或代码作者，因此绝大多数能力信号都能从对话日志提取。

分析分两个阶段：

1. **会话级抽取**：逐个会话处理，原始对话全文只在此阶段读入一次，产出会话特征档案（包括统计数字、会话内容摘要、用户指令片段和行为特征）。这一步不评分，只把会话压缩成供综合判断的素材。
2. **跨会话综合评估**：针对同一个人，读取其周期内所有会话的特征档案，一次性同时评完底层 4 维和上层 4 维，给出周期分。评分调用收敛到每人周期一次，每个分数可追溯到支撑它的会话特征档案以便复核。

补充说明：

1. 成本数据（token 数、轮数、用时）作为统计参考因子喂入所有维度的评估，不单独打分
2. 由于对话日志的工具可见度有限（通常只知道用了工具及次数，看不到工具定义、调用参数和 system prompt），这些维度不从工具配置本身判断，而从行为模式判断

底层 4 维：

1. **任务适配判断力**：看交给 AI 的任务是否琐碎、是否过度依赖、出错时是否盲从
2. **指令与 prompt 设计**：看指令清晰度、背景约束、复杂任务的拆解与结构化。信号最硬
3. **对话驾驭**：看上下文组织、适时开新会话、出错后的迭代纠错与批判性推进
4. **工具与 Skill 调用合理性**：看调用频率与时机。受工具可见度限制，调用是否合理难以评准，评分置信度较低

上层 4 维：

1. **Harness 编排驾驭**（Harness 思想）：看系统性组织 agent 工作的行为（步骤划分、工具组合、角色边界），评估验证看构建后是否让 AI 验证检查并形成闭环
2. **Skill 编写能力**：看是否主动将工作创建为 skill 并做修改迭代
3. **价值产出质量**：评产出端的价值，即用 AI 做出来的东西值不值得，区别于底层维度评的是会不会用。因对话日志看不到产出的最终去向（代码是否合并、方案是否采纳、决策是否落地），只能从对话内部的过程信号反推结果。判断锚点：
   1. 任务价值性：会话承载的任务本身有没有业务价值，对照低价值重复劳动、纯试探
   2. 产出本身的质量：结构化程度、具体性、论证支撑，对照空泛套话
   3. 净有效产出比：有价值的产出会话占总会话的比例
4. **知识沉淀与复用**：看 prompt 模板与方法跨会话迁移、经验固化

注意各维度间的切分，避免重复计分：
1. Skill 编写能力与知识沉淀与复用都涉及把经验做成 skill：前者看 skill 载体的主动创建与迭代，后者看广义复用与经验固化
2. 价值产出质量与任务适配判断力（底层）有重叠：任务适配判断力评会不会把对的活交给 AI，价值产出质量评这件活值不值得做且做得出来
3. 价值产出质量与 Harness 编排驾驭都涉及产出：Harness 评编排过程是否系统化，价值产出评最终产出值不值得
4. AI 管理能力与上层 4 维：上层 4 维走对话分析评会不会用 AI，AI 管理能力走主动测试场景题评能不能像管理者一样驾驭 AI，数据源物理隔离不重复计分

**主线二：主动测试**（首期产品化为两个测评）

主动测试定位为补充手段，覆盖对话日志无法评的能力项。首期聚焦两个产品，用户作答、AI 阅卷，其中 AI 管理能力题由 LLM 生成、九型人格采用标准量表。最小化使用的原则不变：主动测试会给员工增加负担，测多了频率必然拉低，对话分析被动、无负担、可高频运行，更贴合盘点目标。冷启动场景下新员工无对话数据，主动测试作为画像主要支撑。

**测评一：AI 管理能力**（新增高阶维度）

参考常规领导力胜任力方法论，迁移到管理 AI 的场景。衡量的不是会不会用 AI 干具体活（那是 AI 使用能力 8 维的事，走对话分析），而是能不能像管理者一样驾驭 AI 资源。数据来源限定为主动测试场景题，与对话分析的上层 4 维物理隔离，避免重复计分。

按 5 个子能力分别出场景题，每题含情境简述与作答要求，选项直接写在作答要求文本中不单独建结构，员工作答通过与 AI 逐题对话完成，AI 结合对话过程阅卷，每个子能力给分且可追溯到具体题与作答：

1. **目标设定与对齐**：给一个模糊业务目标，让用户拆解为 AI 可执行的任务体系，评拆解的清晰度与目标对齐
2. **授权与分工**：给多个任务与多个 agent/工具，让用户做分工决策，评是否过度授权（全丢 AI）或不会授权（事事亲为）
3. **监督与验收**：给一段含瑕疵的 AI 产出，让用户审查，评是否发现质量问题并形成闭环
4. **风险与担责**：给一个 AI 给出可疑建议的情境（含幻觉或越权风险），让用户判断是否采纳，评风险识别与人的担责
5. **人机协作设计**：给一个工作流，让用户划分人机边界，评协作分工的稳定性

**测评二：九型人格**（性格测评）

性格测评采用九型人格，引入经过验证的标准九型量表作为固定题库，用户作答，AI 基于作答结果判定主型、翼型与 9 型倾向分布。

定位说明：九型人格实证基础弱于大五等标准化量表，故采用标准量表而非 LLM 即兴出题，把不可靠性压到最低，AI 只承担型别判定。初期作为发展性与参考性测评，用于自我认知与团队风格理解，不进入硬性评分聚合。是否纳入 MVP 评分留 PRD 阶段决策。

**其余通用素质项**

通用素质 8 项完整保留在能力模型中，产品化范围与裁剪由产品在 PRD 阶段定夺，需求澄清阶段不做此项决策。原型与首期 MVP 不纳入通用素质，维度配置页不呈现该模块，待 PRD 决定启用时机后再补回。

主动测试的发起与执行沿用既有机制，运营为单次定向发起：HR 按需对特定人员单次定向发起，每次生成一次性作答链接推送，员工提交后失效。题库分两路，AI 管理能力题由 LLM 动态生成、选项写在作答要求文本中不单独建结构，九型人格引入标准量表作固定题库，审核统一为 HR 批量标记驳回制、不逐题审核；员工作答通过与 AI 逐题对话完成，阅卷由 LLM 结合对话过程评估、可复现。

运营分双模式：

1. 全公司定期批量分析由系统按周期自动跑，覆盖全员
2. HR 手动定向分析按需触发，选定某人与某时间段

两种模式共享同一套评分引擎。

产出有两部分：

1. **个人能力画像**：在使用活跃度基线之上展开，包含多维雷达图、每个维度的分数与文字解读、针对短板生成的培训建议；活跃度作为基线单独呈现，对话数据不足导致能力维度降权的情况一并标注
2. **团队汇总看板**：展示整体能力分布、短板人群识别、未使用人群标识、共性短板对应的团队级培训方向建议（个人级培训建议落在个人画像，不在看板呈现）。受首期无组织架构的约束，看板先做全公司整体聚合，按部门钻取后置

高频场景集中在：

1. 周期批量评分跑批
2. HR 进入工作台首页总览本期评估态势与需要关注的人
3. HR 查看团队看板识别短板人群与未使用人群
4. HR 查看个人画像与培训建议
5. HR 发起主动测试并追踪完成情况
6. HR 配置维度权重与审核题库

### 四、核心目标与管控

根本目标是能力盘点与培训提升：

1. 看团队整体能力分布，识别短板人群
2. 给每个人针对性的培训建议
3. 追踪个人能力的历史趋势

这一定位属于低风险用途：评分独立于绩效考核、晋升、调薪等硬性人事决策。由此带来的好处是评分对精度的容错较高，无需扛可申诉、可复核的重担，但要求评分能解释、能指导培训。每个维度分数可追溯到具体会话或测试，正是服务于这一可解释诉求。

痛点优先级排序如下：

1. **范围风险居首**：能力模型覆盖面广，一次性全实现的范围大、周期长，性格、胜任力、价值观三个无独特数据源的模块最容易拖慢整体或烂尾，是 MVP 范围裁剪的首要候选。具体裁剪到什么程度留待 PRD 阶段决策。
2. **评分偏差次之**：LLM-as-judge 存在系统性偏差，初期评分作为参考而非定论，后续随数据积累迭代调优。
3. **冷启动排第三**：新员工无对话数据，靠主动测试撑起画像，对话维度数据不足时降权处理。
4. **隐私风险贯穿全程**：对话原文涉及敏感信息，隐私方案要严格执行。

评分基准：

1. 以绝对分为主，带标准锚点，可追踪个人进步
2. 辅以团队内百分位看相对位置
3. 聚合路径是维度分 → 模块分 → 可选总览分
4. 权重初期取经验值，HR 可在后台调整

这些量化口径在初期都带有经验性质，需要随数据积累迭代。

成本核算的主要维度是 LLM 调用量：

1. 一个活跃员工一周可能产生数十个会话
2. 会话级抽取逐会话调用大模型压缩成特征档案，跨会话综合评估每人周期一次
3. 全公司批量分析一次的调用量仍相当可观

中型规模下需要把成本预算、队列控制、跑批节流纳入设计，LLM 调用与计费走平台配置的大模型。

批量跑批还需配套评分失败的兜底口径：

1. 全公司一次跑批调用量大，个别会话的抽取调用会因模型限流或异常、上下文超限等原因失败
2. 失败会话标记为待重试，按固定次数自动重试
3. 仍失败的降级为仅保留统计上下文、跨会话评估时该会话特征缺失，当期评估照常推进
4. 失败比例超过阈值时触发告警，由 HR 决定是否补跑

重试次数与阈值的具体取值留到架构设计阶段量化。

### 五、内外部约束

合规与隐私是首要约束：

1. 对话原文仅用于 LLM 评分计算
2. 系统只存评分与脱敏理由，不长期展示原文
3. 运营人员只看评分和画像，看不到原始对话
4. 数据基础是员工使用公司提供的 sili-smart-api 网关产生的对话记录

员工本人不是平台用户：

1. 无任何系统入口，看不到画像与评分理由
2. 这与愿景文档原设定（员工可见自己完整画像用于自我提升）不同，是本次澄清的产品决策
3. 员工只作为被测评对象与画像数据来源存在
4. 培训建议的触达由运营人员转达

通用素质 8 项的实现方式差异构成一项约束：

1. 性格采用九型人格，引入标准量表作固定题库，AI 只做型别判定；实证基础弱，初期作为参考性测评，不进入硬性评分聚合
2. 胜任力、价值观两项 AI 增值有限、依赖外部成熟手段，没有独特数据源，是 MVP 范围裁剪的首要候选，裁剪决策留 PRD。首期 MVP 通用素质整体不纳入，原型维度配置页移除该模块。

技术约束来自既定技术栈：

1. 后端用 Go，复用 sili-smart-api 团队经验
2. 前端为 React 19 + TypeScript，构建用 Rsbuild
3. 路由与数据请求用 TanStack Router 和 TanStack Query
4. 状态管理用 Zustand
5. 样式用 Tailwind CSS 4
6. UI 组件用 shadcn/ui 加 @base-ui/react
7. 图表用 Recharts
8. 表格用 TanStack Table
9. 表单用 React Hook Form 加 Zod
10. 前端栈完全对齐 sili-smart-api，可复用其 ai-elements 组件与样式体系
11. UI 组件库固定用 shadcn/ui，与 Ant Design 设计语言不同，二者不可混用
12. 自有业务数据存 PostgreSQL，对话数据来源为 ClickHouse
13. 工程前提是所有维度模块共享通用评估引擎底座

组织与协作约束有三点：

1. 首期不引入组织架构，按团队划分可见范围与按部门钻取后置，团队看板首期为全公司整体聚合
2. 平台账号不区分角色、统一全权，员工不是平台用户，无任何入口
3. 与 sili-smart-api 松耦合，依赖其接口稳定性与集成密钥可用性，接口字段能力（如 `/api/user` 是否含组织信息）需要在架构设计阶段进一步确认
