# 技术组件规格说明书

## 1. 概述

### 1.1 组件名称
LLM 调用底座（LLMCallBase）

### 1.2 组件描述
全系统所有 LLM 调用的统一出口，只提供流式对话补全。底座读取配置域排他启用的唯一模型，按模型服务商归属协议（OpenAI 兼容 /v1/chat/completions 或 Anthropic Messages）发起流式对话补全，统一承载鉴权、超时、指数退避重试、全局并发限制与排队、上下文超限处理。协议构造、鉴权头与流式解析全部由成熟开源 SDK 承担，底座不手写任何协议层代码。

### 1.3 创建背景
对话分析的特征抽取、跨会话综合评估，题库的 AI 管理能力题生成，主动测试的 AI 阅卷，四处都要调用 LLM。若各自手写 HTTP 请求，会为每类协议重复实现请求构造、鉴权头、流式解析、错误识别，代码重复且易错，还难以统一节流与重试策略。

PRD T2 把 LLM 调用抽成技术底座，作为全系统唯一出口。配置域 P2_SYS_001 把模型按服务商分两类协议：DeepSeek、OpenAI、智谱 GLM 走 OpenAI 兼容协议，Anthropic 走 Anthropic 协议，第三方代理按所选服务商归属协议接入。底座据此选用两套成熟 SDK 分协议适配，把协议转换工作全部交给 SDK，自身只保留统一接口、重试、并发限制、超时与 token 处理这些横切能力。

选型依据：sashabaranov/go-openai 是 Go 社区事实标准的 OpenAI 兼容客户端，支持自定义 BaseURL、流式、自配 HTTP 超时，覆盖 DeepSeek、OpenAI、GLM 及三方代理；anthropics/anthropic-sdk-go 是 Anthropic 官方 Go SDK，走原生 Messages 协议。两者都不需要手写协议转换。

### 1.4 技术栈

| 技术 | 版本 | 用途 |
|------|------|------|
| sashabaranov/go-openai | v1.7.0+ | OpenAI 兼容协议客户端，DeepSeek/OpenAI/智谱 GLM/三方代理 |
| anthropics/anthropic-sdk-go | v1.47.0+ | Anthropic 原生 Messages 协议客户端 |
| pkoukk/tiktoken-go | 最新 | BPE token 计数，上下文超限预检，支持离线 BPE 加载 |
| Go | 1.25 | 后端运行时，项目既定 |

> 指数退避重试由底座自研实现（internal/integration/llm/retry.go，含 Retry-After 尊重），不引入 cenkalti/backoff/v4，见 7.3 变更记录 v1.3。

## 2. 组件接口

### 2.1 能力清单

| 序号 | 能力名称 | 能力类型 | 说明 |
|------|---------|---------|------|
| 1 | 流式对话补全 StreamChat | 基础 | 唯一对话入口，逐块返回增量内容，调用方拼装即得完整回复 |
| 2 | 上下文超限处理 | 基础 | 调用前按模型上下文预算预检 token，超限错误映射为领域错误 |
| 3 | 指数退避重试 | 基础 | 对限流与瞬时错误按指数退避重试，429 尊重 Retry-After 头 |
| 4 | 全局并发限制与排队 | 基础 | 同时在飞请求不超过 4，超出的按到达顺序进入队列排队 |
| 5 | 启用模型解析 | 基础 | 读取配置域排他启用模型，按服务商归属协议选择适配器 |

> **能力类型说明**：基础=核心必需能力 | 高级=增强型能力 | 扩展=可选能力。本组件能力均为基础，无高级与扩展项。

### 2.2 输入定义

#### 参数列表

| 参数名 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| req.Messages | []ChatMessage | 是 | 无 | 对话消息序列，role 限定 system/user/assistant |
| req.Temperature | *float64 | 否 | nil | 采样温度，nil 用服务商默认 |
| req.MaxTokens | int | 否 | 0 | 生成 token 上限，0 用服务商默认；Anthropic 协议 max_tokens 必填，0 时底座取 4096 |
| cfg.Timeout | time.Duration | 否 | 10min | 单次调用超时，覆盖从建连到流式 body 读毕全程（两条协议路径同语义） |
| cfg.MaxRetries | int | 否 | 3 | 重试次数，架构文档初版值 |
| cfg.InitialBackoff | time.Duration | 否 | 30s | 指数退避初始间隔，倍增 |
| cfg.MaxBackoff | time.Duration | 否 | 120s | 指数退避上限 |
| cfg.RetryOnStatus | []int | 否 | 429,500,502,503,504 | 重试的 HTTP 状态码 |
| cfg.MaxConcurrency | int | 否 | 4 | 全局同时在飞请求硬上限，超出进入队列排队 |
| cfg.QueueSize | int | 否 | 1024 | 排队请求上限，满时返回 ErrQueueFull |
| cfg.TokenBudget | int | 否 | 0 | 单请求上下文预算 token，0 不预检 |
| cfg.TokenCounter | TokenCounter | 否 | tiktoken-go | token 计数实现，可替换 |

请求与配置的类型定义：

```go
// ChatRequest 一次对话补全的统一请求，模型不在此指定，恒取当前排他启用模型
type ChatRequest struct {
    Messages    []ChatMessage
    Temperature *float64
    MaxTokens   int
}

type ChatMessage struct {
    Role    string // system / user / assistant
    Content string
}

// Config 底座横切行为配置
type Config struct {
    Timeout        time.Duration
    MaxRetries     int
    InitialBackoff time.Duration
    MaxBackoff     time.Duration
    RetryOnStatus  []int
    MaxConcurrency int // 全局在飞硬上限，默认 4，不可禁用
    QueueSize      int
    TokenBudget    int
    TokenCounter   TokenCounter
}
```

### 2.3 输出定义

#### 返回值

| 方法名 | 参数 | 返回值 | 说明 |
|--------------|------|--------|------|
| StreamChat | ctx, ChatRequest | Stream, error | 唯一对话入口，Stream 逐块读取，io.EOF 结束 |

```go
// Stream 流式读取接口，调用方拼装全部 Recv 块即得完整回复
type Stream interface {
    Recv() (StreamChunk, error)          // 读下一块增量，正常结束返回 io.EOF
    Close() error
    Usage() (prompt, completion int)     // 流结束后返回最终 token 用量，未获取为 0
}

type StreamChunk struct {
    Content string // 本块增量内容
}
```

#### 错误码定义

底座把 SDK 与 HTTP 层错误收敛为统一的领域错误 `LLMError`，携带稳定 Code 供调用方分类处置。流建立与流读取（Recv）两阶段的错误均收敛；ctx 取消/超时优先透传原始语义。

| 错误码 | 触发条件 | 处理建议 |
|--------|------|---------|
| ErrAuth | 401，API Key 失效或无权 | 提示运营人员检查大模型配置页密钥，进入密钥轮换 |
| ErrRateLimited | 429 重试耗尽 | 降低触发频率或调低并发，按限流窗口重调度 |
| ErrQueueFull | 排队请求数超 QueueSize | 降低触发频率或增大 QueueSize，见 2.4 能力4 |
| ErrContextLengthExceeded | 请求 token 超模型上下文窗口 | 截断或分片输入，见 2.4 能力2 |
| ErrTimeout | 单次调用超时且重试耗尽 | 检查服务商可用性与网络，增大超时或降并发 |
| ErrRetryExhausted | 5xx 重试耗尽仍失败 | 走 fallback 降级策略，会话标记特征缺失 |
| ErrProviderUnavailable | 未配置启用模型或服务商不可达 | 检查配置域模型清单与网络连通性 |
| ErrUnknown | 其他错误 | 打日志定位，按内部错误处理 |

### 2.4 能力详细说明

#### 能力1: 流式对话补全 StreamChat

**描述**: 全系统唯一的对话补全入口，只走流式。底座读取启用模型，按服务商归属协议调用对应 SDK 流式接口，逐块返回增量内容；调用方拼装全部块即得完整回复，这是特征抽取、跨会话评估、出题、阅卷的统一路径。token 用量在流结束后经 Usage 获取。

**接口定义**:
```go
StreamChat(ctx context.Context, req ChatRequest) (Stream, error)
```

**调用示例**:
```go
client := llm.New(cfg, modelProvider)
stream, err := client.StreamChat(ctx, llm.ChatRequest{
    Messages: []llm.ChatMessage{
        {Role: "system", Content: "你是人才测评专家"},
        {Role: "user", Content: "压缩以下会话为特征档案"},
    },
    MaxTokens: 2000,
})
if err != nil { return err }
defer stream.Close()
var sb strings.Builder
for {
    chunk, err := stream.Recv()
    if errors.Is(err, io.EOF) { break }
    if err != nil { return err }
    sb.WriteString(chunk.Content)
}
_, _ = stream.Usage() // 日志记录 token 用量
```

**注意事项**:
- 请求不携带模型名，恒取当前排他启用模型，调用方无需感知模型切换。
- 需要完整回复的场景（抽取、评估、阅卷）同样走流式拼装，底座不提供一次性返回。
- 重试仅覆盖流建立阶段（StreamChat 返回前）：建立失败按重试策略重发，成功前无块产出，不产生重复内容。流读取阶段（Recv 过程中）的连接中断不重试，错误直接上抛调用方处理。
- 隐私架构在底座外部落地：底座无状态，不持久化任何输入输出，原文仅在调用方内存中存在。
- API Key 永不进入日志与错误信息，SDK 层异常只透出状态码与稳定错误码。

#### 能力2: 上下文超限处理

**描述**: 调用前按模型上下文预算预检输入 token，超限返回 ErrContextLengthExceeded，避免调用直接撞服务商 400；服务商返回 context_length_exceeded 时同样映射为该错误。

**接口定义**:
```go
// TokenCounter 可替换的计数实现，默认 tiktoken-go
type TokenCounter interface {
    CountTokens(ctx context.Context, model string, messages []ChatMessage) (int, error)
}
```

**调用示例**:
```go
cfg := llm.Config{
    TokenBudget:  32000, // 模型上下文窗口的预留预算
    TokenCounter: tiktokencount.New(counter, fallback),
}
stream, err := client.StreamChat(ctx, req)
if errors.Is(err, llm.ErrContextLengthExceeded) {
    // 截断消息或分片后重试
}
```

**注意事项**:
- tiktoken-go 按模型名取 BPE 编码，未知模型回退到 rune 级启发式估算，不阻塞调用。
- BPE 词表首加载需网络，生产离线环境用 tiktoken_loader 离线加载器预置词表，见 4.3。
- TokenBudget 建议取模型上下文窗口的 80%，留出生成空间，具体值由调用方按模型配置。

#### 能力3: 指数退避重试

**描述**: 对限流与瞬时错误按指数退避重试。429 优先尊重服务商 Retry-After 头，无该头或为 5xx 时按初始间隔 30 秒倍增退避，重试耗尽返回对应错误码。

**接口定义**:
```go
// 内置重试策略，由 Config 驱动，调用方无需直接接触
func retryWithBackoff(ctx context.Context, cfg Config, fn func() error) error
```

**调用示例**:
```go
cfg := llm.Config{
    MaxRetries:     3,
    InitialBackoff: 30 * time.Second,
    MaxBackoff:     120 * time.Second,
    RetryOnStatus:  []int{429, 500, 502, 503, 504},
}
```

**注意事项**:
- 401、400 等确定性问题不重试，直接返回对应错误码，避免浪费配额。
- 重试参数为架构文档初版值，随跑批数据积累迭代调整，全部可配置。

#### 能力4: 全局并发限制与排队

**描述**: 底座全局同时在飞请求不超过 4，超出的按到达顺序进入 FIFO 队列排队，队列满时返回 ErrQueueFull。该限制是底座硬约束，作用于所有调用方，与 worker 并发度无关，worker 并发度只控制任务处理并行度。架构文档 3.1.2 已同步该口径。

**接口定义**:
```go
cfg := llm.Config{
    MaxConcurrency: 4,    // 全局在飞硬上限
    QueueSize:      1024, // 排队上限
}
```

**调用示例**:
```go
// 在飞请求达到 4 时，第 5 个请求进入队列等待，前面的完成后按到达顺序放行
stream, err := client.StreamChat(ctx, req)
```

**注意事项**:
- 队列按到达顺序 FIFO 放行，先到先得，无优先级抢占。
- 队列排队受 ctx 取消约束，取消时返回 ctx 错误而非无限等待。
- 排队不占用在飞额度，只在放行后才计入在飞并发。
- QueueSize 防内存积压兜底，默认 1024；跑批高峰期持续打满需降低触发频率或增大 QueueSize。

#### 能力5: 启用模型解析

**描述**: 底座经 EnabledModelProvider 读取配置域排他启用的唯一模型，按服务商归属协议选择 go-openai 或 anthropic-sdk-go 适配器，并缓存适配器复用底层 HTTP 连接。

**接口定义**:
```go
// ModelConfig 底座消费的启用模型参数，由配置域实现 provider 时填充
type ModelConfig struct {
    Provider string // deepseek / openai / zhipu / anthropic
    ModelID  string // 服务商 model 参数，如 deepseek-chat
    BaseURL  string // 自定义 API 地址，空走服务商默认
    APIKey   string // 服务商密钥
}

// EnabledModelProvider 由配置域（P2_SYS_001）实现并注入，底座不依赖配置域实现
type EnabledModelProvider interface {
    GetEnabledModel(ctx context.Context) (ModelConfig, error)
}
```

**调用示例**:
```go
// 配置域实现：读取大模型配置表排他启用记录，翻译为 llm.ModelConfig
func (s *ModelConfigService) GetEnabledModel(ctx context.Context) (llm.ModelConfig, error) {
    m, err := s.repo.FindEnabled(ctx) // 排他启用唯一模型
    if err != nil { return llm.ModelConfig{}, err }
    return llm.ModelConfig{
        Provider: m.Provider,
        ModelID:  m.ModelID,
        BaseURL:  m.BaseURL,
        APIKey:   m.APIKey,
    }, nil
}
```

**注意事项**:
- 配置域在运行时切换启用模型，底座每次调用重新解析，切换即时生效，无需重启。
- 无启用模型时返回 ErrProviderUnavailable，配置域保证始终至少一个启用模型。
- Provider 归属协议映射：deepseek/openai/zhipu 走 OpenAI 兼容适配器，anthropic 走 Anthropic 适配器，第三方代理按所选服务商归属。

### 2.5 使用示例

#### 基础用法

与能力1 调用示例相同，区别仅在以 `defaultConfig()` 代指默认配置构造 client，流式拼装步骤见 2.4 能力1。

```go
client := llm.New(defaultConfig(), modelProvider)
// 流式拼装步骤见 2.4 能力1 调用示例
```

#### 高级用法

```go
// 上下文预算 + 全局并发限制与排队
cfg := llm.Config{
    Timeout:        10 * time.Minute,
    MaxRetries:     3,
    InitialBackoff: 30 * time.Second,
    MaxBackoff:     120 * time.Second,
    MaxConcurrency: 4,    // 全局在飞硬上限
    QueueSize:      1024, // 排队上限
    TokenBudget:    32000,
}
client := llm.New(cfg, modelProvider)
stream, err := client.StreamChat(ctx, llm.ChatRequest{Messages: messages})
```

#### 完整示例

```go
// 完整集成：经 Wire 注入 modelProvider 后，engine 调用方直接使用
import (
    "errors"
    "io"
    "strings"

    "sili-smart-hr/backend/internal/integration/llm"
)

func RunExtraction(ctx context.Context, client llm.Client, prompt, text string) (string, error) {
    stream, err := client.StreamChat(ctx, llm.ChatRequest{
        Messages: []llm.ChatMessage{
            {Role: "system", Content: prompt},
            {Role: "user", Content: text},
        },
    })
    if err != nil {
        if errors.Is(err, llm.ErrRateLimited) || errors.Is(err, llm.ErrQueueFull) {
            // 会话标记待重试，交给 fallback
        }
        return "", err
    }
    defer stream.Close()
    var sb strings.Builder
    for {
        chunk, err := stream.Recv()
        if errors.Is(err, io.EOF) { break }
        if err != nil { return "", err }
        sb.WriteString(chunk.Content)
    }
    return sb.String(), nil
}
```

## 3. 技术约束

### 3.1 性能要求

| 指标 | 要求 | 说明 |
|------|------|------|
| 底座本地开销 | ≤ 50ms | 不含服务商网络往返，覆盖协议适配、token 预检、并发排队 |
| 首 token 延迟 | 由服务商决定 | 底座不引入额外串行环节，延迟主要取决于模型与服务商网络 |
| 并发上限 | 全局同时在飞 ≤ 4 | 底座硬约束，超出进入队列排队，与 worker 并发度无关 |
| 排队上限 | 默认 1024 | 队列满时返回 ErrQueueFull，防内存积压 |
| 上下文预算 | 模型窗口 80% | TokenBudget 由调用方按模型配置，建议取窗口 80%，默认 0 不预检；超限预检不调用服务商 |

### 3.2 兼容性要求

#### 版本兼容性

| 依赖 | 版本要求 | 说明 |
|------|---------|------|
| Go | 1.25 | 项目既定运行时，anthropic-sdk-go 要求 Go 1.24+，满足 |
| sashabaranov/go-openai | v1.7.0+ | v1.7.0 起默认 /v1/chat/completions 路径，旧版路径错误 |
| anthropics/anthropic-sdk-go | v1.47.0+ | 官方 SDK，要求 Go 1.24+ |
| pkoukk/tiktoken-go | 最新 | 纯 Go BPE 分词，编码实例并发安全 |

#### 协议兼容性

| 协议 | 适配 SDK | 服务商 |
|------|---------|--------|
| OpenAI 兼容 /v1/chat/completions | go-openai | DeepSeek、OpenAI、智谱 GLM、OpenAI 兼容第三方代理 |
| Anthropic Messages | anthropic-sdk-go | Anthropic、Anthropic 兼容第三方代理 |

API 地址填 base URL 时按 go-openai 约定带 /v1 根路径（如 https://api.deepseek.com/v1），底座拼 /chat/completions；anthropic-sdk-go 由客户端构造函数承载 base URL，地址留空走服务商默认。

### 3.3 安全要求

| 安全项 | 要求 | 实现方式 |
|--------|------|---------|
| 密钥保护 | API Key 不落日志、不进错误信息、不被 SDK 透出 | 适配层只透出 HTTP 状态码与稳定错误码，日志脱敏 |
| 密钥来源 | 密钥由配置域加密存储与下发，底座不持久化 | 每次调用经 EnabledModelProvider 获取，内存短暂持有 |
| 隐私隔离 | 底座无状态，不存储输入输出 | 对话原文仅在调用方内存存在，抽取后丢弃，与隐私架构一致 |
| 传输安全 | 与服务商通信走 HTTPS | 默认 https base URL，自定义地址由配置域校验 URL 格式 |
| 凭据最小暴露 | 日志与监控指标不携带密钥与原文片段 | 打日志只记录模型名、token 用量、耗时、排队等待、重试次数、结果 |

## 4. 集成方式

### 4.1 安装方式

```bash
# 在 hr-backend/ 下引入依赖
go get github.com/sashabaranov/go-openai@v1.7.0
go get github.com/anthropics/anthropic-sdk-go@v1.47.0

```

### 6.3 告警规则

| 告警名称 | 触发条件 | 严重程度 | 处理建议 |
|---------|---------|---------|---------|
| 调用失败率超阈 | 成功率低于 95% 持续 10 分钟 | 高 | 检查服务商可用性、密钥是否失效、限流状态 |
| 队列积压 | 排队数持续打满或等待超阈 | 中 | 降低触发频率或增大 QueueSize，检查服务商响应速度 |
| 上下文超限频发 | 单周期 ErrContextLengthExceeded 持续增长 | 中 | 调大 TokenBudget 或分片输入，检查模型窗口配置 |
| 密钥失效 | 连续 ErrAuth 命中 | 高 | 立即轮换 API Key，检查大模型配置页 |
| 429 集中命中 | 单周期 429 占比异常 | 中 | 降低并发或调整触发节奏，按限流窗口重调度 |

跑批失败超阈告警信号由 T6 fallback 汇总下发至工作台 F11 待处理项，底座只暴露指标，不直接触达页面。

### 6.4 故障排查

**问题1: 调用返回 ErrAuth**
- 现象: 连续 401，日志 code=ErrAuth
- 原因: API Key 失效、被轮换或无权访问该模型
- 解决: 运营人员在大模型配置页查看并更新密钥，确认模型 ID 有权限

**问题2: 调用返回 ErrRateLimited**
- 现象: 日志大量 429，重试后仍失败
- 原因: 触发频率超服务商限流阈值，模型限流窗口未到
- 解决: 降低 MaxConcurrency，或推迟该批调用，按 Retry-After 重试

**问题3: 调用返回 ErrContextLengthExceeded**
- 现象: 日志 code=ErrContextLengthExceeded
- 原因: 输入消息超模型上下文窗口，常见于长会话特征抽取
- 解决: 增大 TokenBudget 配置无效时，对输入截断或分片，跨会话评估控制喂入特征数量

**问题4: 调用超时**
- 现象: 日志 code=ErrTimeout，duration 接近超时上限
- 原因: 服务商响应慢、网络抖动、大模型推理长
- 解决: 增大 cfg.Timeout，检查服务商可用性，评估长推理模型单独配置超时

**问题5: 调用返回 ErrQueueFull**
- 现象: 日志 code=ErrQueueFull，queue_depth 打满
- 原因: 排队请求数超 QueueSize，常见于跑批高峰期叠加其他调用
- 解决: 降低触发频率，或按实际并发需求增大 QueueSize，观察排队等待是否回落
