## 1. 项目背景

sili-smart-hr 是面向企业内部的综合人才测评平台，用 AI 完成对人员多维度能力的评估。所属领域为人力资源数字化中的能力测评与人才发展细分赛道，定位为内部系统能力，服务企业自身的团队能力盘点与培训提升。

在数据价值链上，本系统处于兄弟系统 sili-smart-api（基于 new-api 的 LLM 网关）的下游，是数据消费方。它把 sili-smart-api 沉淀的员工 AI 对话日志转化为能力评估信号，再叠加主动测试，形成个人与团队的人才画像。两者松耦合：本系统经集成密钥 Bearer 调用 sili-smart-api 的会话日志接口，LLM 评分与阅卷走平台在大模型配置页自配的模型。

核心差异化在于 AI 使用能力评估。市面通用测评工具无法分析员工的 AI 使用水平，因为只有 sili-smart-api 的对话日志能提供这个数据源。这项独有资产决定了本系统的竞争位势无法被通用工具替代。

系统运作依赖三类关键资源。一是对话日志数据资产，归属 sili-smart-api，存于 ClickHouse，是 AI 使用能力（底层 4 维加上层 4 维）评分的信号来源。二是 LLM 调用能力，由平台在大模型配置页排他启用的模型承载，底层维度的全量评分、AI 管理能力题生成与阅卷统一走该模型。三是本系统自有资产，存于 PostgreSQL，包括评分记录、画像、看板、维度与权重配置、题库、主动测试记录。工程上还有一个待建的通用评估引擎底座，承担出题、LLM 阅卷、多维打分、聚合、报告生成，所有维度模块共享。

被测评对象与平台用户物理隔离。被测评对象为首期全公司 100 至 500 名员工，作为评估数据来源与画像主体，本身不是平台用户，无任何系统入口。平台账号统一全权，登录即拥有全部功能，账号体系由平台自管。

## 2. 项目目标

根本目标是能力盘点与培训提升：看团队整体能力分布并识别短板人群，给每个人针对性的培训建议，追踪个人能力的历史趋势。这一定位属于低风险用途，评分独立于绩效考核、晋升、调薪等硬性人事决策，因此评分对精度的容错较高，重点要求评分能解释、能指导培训，每个维度分数可追溯到具体会话或测试。

围绕这一根本目标，平台需支撑三条价值链：一是把被动沉淀的对话数据周期性地转化为能力画像，二是用主动测试补齐对话日志覆盖不到的能力项，三是把画像与看板交付给运营人员消费并指导培训。

首期实施受若干约束引导。能力模型覆盖面广，通用素质 8 项（性格、胜任力、价值观等）在首期 MVP 暂不纳入，集中资源把有独有数据源的 AI 使用能力 8 维、AI 管理能力 5 维、九型人格做扎实。LLM-as-judge 存在系统性偏差，初期评分作为参考而非定论，随数据积累迭代调优。冷启动场景下新员工无对话数据，靠主动测试撑起画像。隐私是贯穿全程的约束，对话原文仅用于评分计算，系统只存评分与脱敏理由，运营人员只看评分和画像，看不到原始对话。

## 4. 功能模块详细说明

> 操作人员总体说明：平台不设角色权限模型，所有平台账号登录后拥有相同功能。本系统识别三类操作主体：测评运营人员（平台账号，统一全权，下文简称"运营人员"）、被测评员工（仅持一次性作答页入口）、评估引擎（系统自动角色）。下文各模块"操作人员定义"据此说明该模块由谁操作。

### 4.1 对话分析评估

#### 4.1.1 模块业务目标

把员工在 sili-smart-api 沉淀的对话行为周期性地转化为能力评分，覆盖 AI 使用能力底层 4 维与上层 4 维，是能力评估的主通道。它被动运行、无负担、可高频，回答员工会不会用 AI。运营人员亦可按需对特定人员发起定向分析，复用同一套评分引擎。

#### 4.1.2 模块业务流程

批量评估流程由系统按运营人员配置的周期自动触发，覆盖全员：拉取本周期累计会话，逐会话抽取特征档案，针对单人一次性完成跨会话综合评估；若单人数据充足则正常评分，数据不足则对相关维度降权；随后汇聚使用活跃度作为基线，生成个人画像，更新团队看板。

定向分析流程由运营人员按需触发：选定某人与某时段，系统拉取该范围会话并抽取特征、综合评估、生成画像，运营人员随后查看定向报告。

#### 4.1.3 功能列表

| 功能 | 子功能 | 说明 |
|:--|:--|:--|
| 周期批量评估 | 拉取本周会话 | 系统在跑批周期到达时自动拉取会话日志以启动全员评估 |
| | 会话特征抽取 | 系统逐会话调用大模型压缩特征以形成评估素材 |
| | 跨会话综合评估 | 系统汇集单人全部特征后一次性调用大模型产出周期能力评分 |
| | 使用活跃度统计 | 系统按规则统计会话频率与轮次以判定活跃、低频或未使用 |
| | 生成个人画像 | 系统汇聚活跃度与能力评分生成个人能力画像 |
| | 更新团队看板 | 系统在全员画像生成后聚合更新团队汇总看板 |
| 手动定向分析 | 选定对象时段 | 运营人员在按需盘点时选择某人与某时段发起定向评估 |
| | 定向评估执行 | 系统在运营人员触发后复用评分引擎完成指定人员评估 |
| | 查看定向报告 | 运营人员在评估完成后查看报告以了解特定人员能力 |

#### 4.1.4 操作人员定义

批量评估的拉取、抽取、综合评估、画像与看板更新由评估引擎（系统自动角色）执行；周期参数与维度权重由运营人员预先配置。手动定向分析的发起与报告查看由运营人员操作，评估执行由系统完成。

#### 4.1.5 对接的外部系统

依赖 sili-smart-api 会话日志库（ClickHouse）作为对话日志数据源，经集成密钥鉴权访问会话日志接口；依赖平台自配大模型完成会话级特征抽取与跨会话综合评估。

#### 4.1.6 模块边界和依赖关系

本模块是能力评估的主通道，向上依赖维度与权重配置（评分口径）、系统配置（周期与大模型）、sili-smart-ap日志集成密钥可用性；向下产出的个人画像与团队看板供结果消费模块使用，失败会话交由异常处置兜底。使用活跃度作为基线独立于能力评分，是能力评分的前提：未使用用户无对话数据，能力维度无从评分。

### 4.2 主动测试评估

#### 4.2.1 模块业务目标

补齐对话日志覆盖不到的能力项，首期产品化为 AI 管理能力与九型人格两个测评。它由运营人员按需单次定向发起，定位为补充手段，会给员工增加负担，因此测多了频率必然拉低，与被动高频的对话分析形成互补。冷启动场景下新员工无对话数据，主动测试是画像的主要支撑。

#### 4.2.2 模块业务流程

测试由运营人员发起，覆盖 AI 管理能力场景题与九型人格两个测评：运营人员选定对象与维度，系统生成一次性作答链接，运营人员复制链接经 IM 或邮件分发（首期推送通道暂未接入，为手动分发）；员工经链接进入作答页提交作答，系统 AI 阅卷评分，结果汇入个人画像；运营人员随后查看测试结果并追踪完成情况。

#### 4.2.3 功能列表

| 功能 | 子功能 | 说明 |
|:--|:--|:--|
| 测试发起 | 选对象维度 | 运营人员发起测试时选择对象与维度定义测评范围 |
| | 单次定向发起 | 运营人员对特定人员单次定向发起以执行一次测评 |
| | 生成作答链接 | 系统在测试发起后生成一次性链接供员工作答 |
| | 推送作答链接 | 运营人员复制作答链接经 IM 或邮件分发以触达员工（首期为手动分发） |
| | 追踪完成情况 | 运营人员在测试进行中查看完成状态以跟进作答进度 |
| 测试阅卷 | AI 阅卷评分 | 系统收到作答后结合对话过程由 LLM 评估产出测试分数 |
| | 阅卷成功更新画像 | 系统在阅卷通过后汇入评分更新个人画像 |
| | 阅卷失败兜底 | 系统在阅卷异常时通过重试或降级保留统计以保障当期推进 |
| 测试管理 | 取消测试 | 运营人员取消未完成测试以作废作答链接 |
| | 重新生成链接 | 运营人员在链接失效或丢失时重新生成以重新触达员工 |
| | 重发作答提醒 | 运营人员在员工未作答时重发作答链接以推动员工作答 |

#### 4.2.4 操作人员定义

测试发起、追踪与管理由运营人员操作；阅卷评分、画像更新与失败兜底由评估引擎（系统自动角色）执行。

#### 4.2.5 对接的外部系统

AI 管理能力题生成与阅卷依赖平台自配大模型；九型人格依赖标准九型量表来源（固定题库，不走生成）；作答链接推送依赖 IM 或邮件推送通道（首期未接入，手动分发）。

#### 4.2.6 模块边界和依赖关系

本模块向上依赖题库管理（供题）、维度与权重配置（评分口径）、大模型可用性；员工作答环节依赖员工作答模块承接。AI 管理能力与对话分析的上层 4 维物理隔离：上层 4 维走对话分析评会不会用 AI，AI 管理能力走主动测试场景题评能不能像管理者一样驾驭 AI，两者数据源不同，避免重复计分。阅卷结果汇入个人画像，与对话分析结果并列呈现。

### 4.3 员工作答

#### 4.3.1 模块业务目标

为员工提供主动测试的一次性轻量作答入口。员工本人不是平台用户，无主入口，仅经此页提交测试作答，作答后链接即失效。该页只承载作答提交，不提供画像、看板、评分理由的任何浏览能力。

#### 4.3.2 模块业务流程

员工收到作答链接后点击进入作答页，通过与 AI 逐题对话完成 AI 管理能力情境题或九型人格量表作答，作答完成后提交答卷，链接随即失效。

#### 4.3.3 功能列表

| 功能 | 子功能 | 说明 |
|:--|:--|:--|
| 测评作答 | 进入作答页 | 员工在收到链接时点击进入开始作答 |
| | AI 逐题对话施答 | 员工作答时与 AI 逐题对话完成情境题或量表作答，选项写在作答要求中、无标准答案 |
| | 提交作答 | 员工在作答完成后提交以交付答卷并使链接失效 |

#### 4.3.4 操作人员定义

由被测评员工（仅一次性作答页入口）操作，员工作答随测试周期性进行，每轮用新链接。

#### 4.3.5 对接的外部系统

无直接外部系统依赖。作答数据经作答提交接口回流至平台，由系统阅卷。

#### 4.3.6 模块边界和依赖关系

本模块是主动测试评估在员工侧的执行入口，依赖主动测试评估已发起并推送有效作答链接。作答页独立于主平台框架，视觉风格保持一致但布局独立，作答提交后由主动测试评估模块接续阅卷与画像更新。

### 4.4 异常处置

#### 4.4.1 模块业务目标

保证全公司批量跑批在个别会话抽取失败时仍能照常推进，失败可控、当期评估不被局部失败阻塞。

#### 4.4.2 模块业务流程

抽取失败的会话标记为待重试，系统按固定次数自动重试；仍失败的降级为仅保留统计上下文，跨会话评估时该会话特征缺失，当期评估照常推进；失败比例超过阈值时触发告警，由运营人员决定是否触发补跑，补跑复用手动定向分析入口。

#### 4.4.3 功能列表

| 功能 | 子功能 | 说明 |
|:--|:--|:--|
| 失败兜底 | 自动重试 | 系统在抽取失败时按固定次数重试以恢复评估 |
| | 降级保留统计 | 系统在重试耗尽时仅保留统计上下文以保障当期推进 |
| | 超阈告警 | 系统在失败比例超阈时告警通知运营人员 |
| | 定向补跑 | 运营人员在告警后触发补跑以补齐缺失会话评估 |

#### 4.4.4 操作人员定义

自动重试与降级保留统计由评估引擎（系统自动角色）执行；超阈告警由系统在工作台与评测运营中心就近呈现；定向补跑由运营人员触发，复用对话分析的手动定向分析入口。

#### 4.4.5 对接的外部系统

无独立外部系统依赖，告警与兜底围绕平台自配大模型的可用性、限流与计费约束设计。

#### 4.4.6 模块边界和依赖关系

本模块监听对话分析评估的失败状态并联动处置，首期不设独立的失败会话列表或补跑页面：重试与降级由评估引擎自动执行，失败比例超阈在工作台告警卡体现，补跑复用手动定向分析入口。待重试次数与告警阈值的具体取值在系统参数页配置。

### 4.5 个人画像

#### 4.5.1 模块业务目标

在使用活跃度基线之上展开个人的多维能力全景，让运营人员了解每个人的能力结构、短板结论与培训方向，并追踪个人能力的历史趋势。培训建议由运营人员线下转达给员工本人。

#### 4.5.2 模块业务流程

运营人员经人员列表或检索定位人员，进入画像详情查看多维能力雷达与解读、短板结论与培训方向、历史趋势与降权标注；团队看板下钻到个人时也进入本模块。

#### 4.5.3 功能列表

| 功能 | 子功能 | 说明 |
|:--|:--|:--|
| 画像查询 | 人员检索 | 运营人员消费时通过列表或检索定位人员 |
| 画像详情 | 多维能力查看 | 运营人员查看画像了解多维能力雷达与解读 |
| | 短板结论与培训方向 | 运营人员阅读核心结论与短板标记确定培训方向，建议线下转达 |
| | 历史趋势查看 | 运营人员对比历史分数追踪进步 |
| | 降权标注查看 | 运营人员查看降权标注了解数据不足维度 |

#### 4.5.4 操作人员定义

由运营人员（平台账号，统一全权）消费，员工本人看不到自己的画像与评分理由。

#### 4.5.5 对接的外部系统

人员信息（人员标识到人名的映射）依赖 sili-smart-api 用户体系，首期仅取人名。

#### 4.5.6 模块边界和依赖关系

### 4.9 题库管理

#### 4.9.1 模块业务目标

为主动测试供给题目，分两路来源：AI 管理能力题由 LLM 动态生成，九型人格引入标准量表作固定题库。统一采用 HR 批量标记驳回制审核，不逐题审核。

#### 4.9.2 模块业务流程

题库分两路进入：系统生成 AI 管理能力场景题（含情境简述与作答要求，选项写在作答要求文本中），或运营人员引入九型标准量表。两路共用同一审核界面但按来源分批、不混审：运营人员逐题过目，只对不合适的题标记驳回，被标记的驳回弃用，未标记的默认通过入库启用，入库后可在题库维护中管理生命周期。

#### 4.9.3 功能列表

| 功能 | 子功能 | 说明 |
|:--|:--|:--|
| 题目生成 | LLM 生成 AI 管理题 | 系统在需补充时通过 LLM 生成扩充题目 |
| | 场景题生成 | 系统为每道场景题产出情境简述与作答要求，选项写在作答要求文本中 |
| 量表引入 | 引入九型量表 | 运营人员在启用九型测评时引入标准量表建立固定题库 |
| 题目审核 | 批量审核入库 | 运营人员按来源分批过目标记驳回或默认入库 |
| | 标记题目驳回 | 运营人员对不合适题目标记驳回弃用 |
| 题库维护 | 题库查询 | 运营人员查询查看题库内容 |
| | 题目状态维护 | 运营人员编辑或启用停用删除以管理题目生命周期 |

#### 4.9.4 操作人员定义

题目生成由评估引擎（系统自动角色）执行，量表引入、题目审核与题库维护由运营人员操作。

#### 4.9.5 对接的外部系统

AI 管理能力题生成依赖平台自配大模型；九型人格依赖标准九型量表来源（具体量表选型与授权方式待定）。

#### 4.9.6 模块边界和依赖关系

本模块向下被主动测试评估依赖（供题），向上依赖大模型可用性。审核机制对生成题与标准量表题统一适用但焦点不同：生成题审场景质量与偏见，标准量表题审本公司适用性。题目均为情境题，选项以自然文本写在作答要求中，不单独建立选项数据结构、不预设标准答案、不做题型枚举分类。

### 4.13 系统初始化

#### 4.13.1 模块业务目标

在系统首次部署、数据库尚无可用账号时，引导首访者完成最小必要初始化，让平台从空白状态进入可登录、可运营的就绪状态，并以一条初始化记录锁定状态，避免空库部署后无人可登录或登录后状态不明。

#### 4.13.2 模块业务流程

系统启动时自检初始化状态：若已存在初始化记录则判定为已就绪，首访探针放行至登录页；若无记录则进入初始化向导。首访者在向导中确认环境就绪项、创建第一个可登录平台账号，提交后系统写初始化记录锁定状态并跳转登录页，此后初始化入口关闭、初始化接口拒绝重复提交。

#### 4.13.3 功能列表

| 功能 | 子功能 | 说明 |
|:--|:--|:--|
| 首次初始化向导 | 初始化状态检测 | 系统启动判定是否已初始化，前端首访探针据此放行登录或进入向导 |
| | 环境就绪自检 | 向导展示数据库类型与连通、缓存连通、密钥就绪等运行底座就绪项 |
| | 创建首个账号 | 首访者在向导中创建第一个可登录平台账号作为运营起点 |
| | 完成初始化 | 系统写初始化记录锁定状态后关闭向导并跳转登录，初始化接口拒绝重复提交 |

#### 4.13.4 操作人员定义

由首访者（部署后第一个打开系统者，通常为运营人员或技术运维）执行；初始化完成后该入口关闭。

#### 4.13.5 对接的外部系统

无直接外部系统依赖，向导聚焦账号创建与状态锁定，不强制配置大模型与集成密钥。

#### 4.13.6 模块边界和依赖关系

本模块是全平台的就绪前置，向上依赖平台认证与账号基建提供账号模型与登录入口判定，向下为登录认证与工作台提供就绪状态。向导聚焦首个账号创建与初始化状态锁定，大模型配置、sili-smart-ap日志集成密钥、维度权重、评估周期等运行时配置不在向导内强制，由各自配置页维护，向导完成后工作台就近提示未完成的配置项。

## 5. Feature 拆分推荐

拆分采用两条泳道，对齐下游两个生成技能。技术 Feature（TECH 类型）承载可复用的技术基座与技术组件，无独立页面，围绕接口与性能约束，由「技术feature生成」技能产出规格；业务 Feature（FEAT 类型）承载面向运营人员的业务功能，有页面归属、独立交付业务价值，由「业务feature生成」技能产出规格。每个 Feature 自包含、可独立开发与验证，下游按 Feature 类型选择技能逐个产出 01_功能需求规格说明书。

### 5.1 拆分原则

**泳道分离**。被多个业务复用、无独立页面、围绕接口与性能约束的技术能力归 TECH；面向运营人员的页面与业务流程归 FEAT。两条泳道分别对齐「技术feature生成」与「业务feature生成」技能，Feature 类型决定下游走哪个技能。

**技术分离**。评估引擎的计算内核（特征抽取、综合评估、聚合、活跃度）、跑批调度、失败兜底、外部集成（LLM、会话日志）、平台运行基座，都是无独立页面的可复用技术能力，各自拆为 TECH。业务 Feature 只承载运营人员的发起、追踪、态势查看、报告与画像消费，不承载 LLM 重计算。题库 LLM 出题、主动测试 AI 阅卷作为各自业务闭环的一环留在 FEAT，底层调用统一走 LLM 调用底座（T2）。

**自包含**。每个 Feature 有清晰的输入输出边界，可独立开发、独立测试。技术 Feature 用单元测试与契约测试验证，喂入构造数据看输出；业务 Feature 用 mock 数据先行验证页面价值，再逐步接入上游真实数据与底座能力。

**依赖有序**。被依赖方优先开发。地基 T1 先行，配置域 F3、F4 先于消费它的引擎 T2、T3、T5、T6，引擎计算 T4、T5 先于跑批调度 T6，评估运营 F6、F7 先于结果消费 F9、F10、F11。

### 5.2 Feature 清单

两个泳道共 18 个 Feature：技术 Feature 6 个（承载评估引擎底座等技术能力，不计入业务功能点），业务 Feature 12 个，功能点合计 27 个，全覆盖需求澄清功能列表。

### 5.3 拆分说明

**技术泳道分四组**。平台基建 T1 是全平台地基，前后端框架、统一响应、双鉴权链路（主平台 JWT 加作答页一次性令牌）、导航布局都在此，account 脚手架已交付登录链路样板，T1 在其上补齐通用基建并固化为可复用技术feature。外部集成 T2、T3 把 LLM 调用与会话日志访问剥离成可复用客户端，是引擎、阅卷、出题的统一调用出口。评估引擎核心 T4、T5 构成周期评估的计算内核：T4 特征抽取把原始对话压缩为脱敏特征档案（隐私架构在此落地，原文不入库），T5 综合评估一次性评完 AI 使用能力 8 维并聚合，叠加活跃度纯规则统计。跑批与韧性 T6 用 Asynq 驱动 T4、T5 执行周期跑批与按需任务，失败兜底的重试、降级、告警信号在此。

**异常处置横切三处**。失败兜底的自动重试与降级保留统计、超阈告警信号落在 T6 的 fallback；定向补跑入口复用 F6 的手动定向分析；超阈告警在工作台 F11 的待处理项呈现。功能点计入 F6，技术内核在 T6。

**业务泳道分四组**。账号与就绪 F1、F2 是平台可登录可运营的前置。配置域 F3、F4 维护模型密钥、评估周期、维度权重与活跃度阈值，是 T2、T3、T5、T6 的运行前提，虽为业务feature但属早期基础设施性质，排在对应技术feature之前。评估运营 F5、F6、F7、F8 中，题库供题先行，对话分析与主动测试共用评测运营中心页面按 tab 分占，员工作答独立路由一次性令牌承接主动测试；LLM 出题与阅卷走 T2 底座。结果消费 F9、F10、F11、F12 只读消费上游数据，个人画像先于团队看板，工作台最后聚合评估态势、测试态势与告警。

**依赖链**：T1 地基，并行启动配置域 F3、F4，外部集成 T2、T3，引擎核心 T4 到 T5，跑批 T6，评估运营 F6、F7（F8 作答承接 F7），结果消费 F9 到 F10 到 F11，F12 操作日志随 T1 之后任意时点落地。
