## API-LIST 批次列表查询与筛选

操作角色：已登录平台账号

前置条件：后端与 Redis 已启动，存在至少一个已登录账号；库内已有批次记录（可由本用例前置的 B1 创建产生）

测试数据：

| id | params |
| --- | --- |
| default |  |
| trig-sch | trigger_type=scheduled |
| trig-bad | trigger_type=xyz |
| st-bad | status=xyz |
| size-101 | page_size=101 |
| size-0 | page_size=0 |
| noauth | 无token |

操作步骤：

1. 以合法 token 调 GET /api/assessment/batches 默认分页
2. 分别传 trigger_type=scheduled / manual / 非法值
3. 分别传 status=running / success / partial_failed / failed / 非法值
4. 传 page 与 page_size 边界值（page_size=10/20/50/100/101/0）
5. 无 token 调一次

| 检查内容 | 预期结果 | 需求依据 |
| --- | --- | --- |
| LIST-OK | 默认查询返回 code=0，list 内 triggered_at 倒序，字段含 id(string)/batch_no/trigger_type/status/stalled 等 | 03 §3.A1：响应 {code:0, data:{list,total,page,page_size}}，按触发时间倒序 |
| LIST-FILTER | 合法枚举值正常过滤；非法枚举返回 code=1400 | 03 §3.A1：trigger_type/status 空串=全部，枚举外返回 1400 |
| LIST-PAGE | page_size=101 实际按 100 返回（响应 page_size=100）；page_size=0 按 10 返回 | 03 §3.A1：page_size 实现 1-100 宽松超集，>100 钳 100，≤0 兜底 10 |
| LIST-AUTH | 无 token 请求返回 HTTP 401 与 code=1003 | 03 §2.1：无 token 返 HTTP 401 + code 1003 |

| id | body |

| no-name | staffs=[{staff_id:x}] |

| bad-mode | target_mode=xyz |

1. 提交合法 specified 请求（2 人、历史时段）

## FLOW-BATCH-RUN 手动批次端到端跑批闭环

操作角色：已登录平台账号（运营人员）

前置条件：Redis + 后端已启动；集成密钥指向真实上游；大模型配置已排他启用一个可用模型；选定 1-2 名真实存在会话数据的人员作为评估对象

操作步骤：

1. 通过 B1 接口发起 specified 批次（选 1-2 人、近一周历史时段）
2. 轮询 A1 列表观察该批次状态与进度推进
3. 批次到达终态后核对 evaluated_count/total_count/covered_session_count/failed_count
4. 核对失败明细接口与人员终态分布
5. 再次对同批同人同时段发起第二个批次（幂等收敛验证）

| 检查内容 | 预期结果 | 需求依据 |
| --- | --- | --- |
| RUN-LIFECYCLE | 批次从 running 推进到终态；终态与失败占比一致（≤10% success，>10% 且 <100% partial_failed，=100% failed） | specs §6.1/§6.2：running → success/partial_failed/failed |
| RUN-PROGRESS | 轮询期间 progress_percent 单调不减 | specs §4.1.4 规则2：进度=终态人数/总人数只增不减 |
| RUN-COVER | covered_session_count ≤ total_session_count，失败人员会话不计入 | specs §5.2.4 规则3：覆盖会话数=成功侧各人会话数之和 |
| RUN-ALERT | 失败占比 >10% 时库内 assessment_alerts 出现该批次一条记录；≤10% 时无记录 | specs §5.2.4 规则4：超阈批次至多一条告警，assessment_alerts 可查 |
| RUN-IDEMPOTENT | 第二批次同人评估大概率 reused 终态，评分结果无重复计分行 | specs §4.1.4 规则3：同人同区间重复评估收敛同一评分 |

## FLOW-SCHEDULED 定时批次周期触发

操作角色：系统调度（Asynq scheduler）

前置条件：后端运行中，scheduler 每分钟投递 batch-tick；评估周期配置可修改（系统参数页或直接改库）

操作步骤：

1. 把周期改为 daily、触发时刻改为 2-3 分钟后的时点
2. 等待 tick 消费命中触发
3. 观察批次列表出现 scheduled 批次与周期窗口正确性
4. 把触发时刻再改为下一分钟验证宽限窗防重复建批
5. 恢复原周期配置

| 检查内容 | 预期结果 | 需求依据 |
| --- | --- | --- |
| SCHED-TRIGGER | 命中触发点后自动创建 scheduled 批次且仅一条；宽限窗内剩余 tick 不会重复建批；daily 批次评估时段为当日 | specs §5.1.4 规则4 + 03 §4.3：触发点 2 分钟宽限窗 + 本周期已建批判定防重复 |
| SCHED-WINDOW | 定时批次评估时段与周期窗口推算口径一致（以 daily 实测，weekly/monthly 依赖单测证据） | specs §5.1.4 规则1：日→当日、周→本周一至本周日、月→本月1日至月末 |
| SCHED-CONFIG-EFFECT | 修改周期配置后，下一次触发按新配置执行，进行中批次不受影响 | specs §4.1.4 规则4：配置变更下次触发生效 |

## FLOW-UPSTREAM-FAIL 上游不可用时整批失败兜底

操作角色：已登录平台账号（运营人员）

4. 打开失败明细核对全员失败与批次级原因
5. 恢复集成密钥，从失败明细按失败对象重新发起补跑

| FAIL-RERUN | 补跑批次成功执行并收敛，原失败批次状态不变（终态不可逆） | specs §5.3.2 步骤5：失败明细按失败对象重新发起补跑 |
