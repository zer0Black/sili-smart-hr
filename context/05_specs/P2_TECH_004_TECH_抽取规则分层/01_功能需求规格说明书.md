# 技术组件规格说明书

## 1. 概述

### 1.1 组件名称

抽取规则分层（SessionExtractorRuleLayering）

### 1.2 组件描述

对 P2_TECH_003 会话特征抽取的裁剪判定链做纯结构性重构：把「框架注入识别规则」从单文件混合实现拆成「通用规则层 + 客户端规则注册表」两层，通用层承载跨客户端共享的判定（role 兜底、打断标记、内嵌 SR 剥离、transcript 区段、工具行保留），各客户端（Claude Code、OpenCode、WorkBuddy、OMO 类插件、自动化客户端）的形态规则各自成文件、经注册表挂载，全部已注册规则并集执行；同时新增客户端签名探测，把会话主客户端识别结果落库为档案列，供观测按客户端拆分与 T5 消费侧归因。出厂态判定行为与基线严格等价（参数页配置了追加前缀的部署态差异见 2.4 能力1 第 2 条），本组件不改变任何抽取产出的语义。

### 1.3 创建背景

基线实现的判定链（classify.go）把全部客户端的注入形态串在一条优先级链里：Claude Code 的 system-reminder 分流、WorkBuddy 的 user_query 复合形态、OMO 插件的工具转写家族、自动化客户端的提示词碎片家族混在同一组常量与同一函数体中，出厂黑名单（config.go 的 injectPrefixesFactory）也是各客户端前缀的平面混排。上游客户端仍在演进（实测已有多时段多人群的新形态持续进入待标定清单），每次新增一个客户端的规则都要在同一条链上插优先级、在同一个平面集合里加前缀，规则间的归属关系只能靠注释维护，长期会让判定链不可读且改动风险随规则数线性放大。

本次重构建立明确的分层契约：通用规则一处定义、全部客户端共享；客户端规则按客户端归属成文件、经注册表挂载、并集执行（不按识别结果定向路由，因混合会话实测普遍：WorkBuddy 包裹 Claude Code 会话、Claude Code 装 OMO 插件并存）；新客户端接入 = 新增一个规则文件 + 注册表一行注册，不触碰既有客户端规则。客户端识别在数据层面可行（上游 SessionDetail 无客户端字段，靠会话内容签名启发式判定），识别结果的价值是观测归因（提取通道参数化属后续演进方向，本期不交付），而非规则路由的正确性依赖。

func AllClientRules() []ClientRules

### 2.4 能力详细说明

#### 能力1: 会话裁剪（分层重构）

> [修改] 本能力内部实现重组为分层结构；三分类语义（框架噪音/规约指纹/保留）、判定优先级链（0 判定范围 → 1 内容语义白名单 → 2 前缀黑名单 → 3 role 兜底，含全部细化裁定）与基线完全一致，唯一权威定义仍在基线文档 2.4 能力1，本节只定义分层契约与执行模型。

**描述**: 判定链执行模型改为「通用层 + 全部已注册客户端规则并集」：

1. **并集执行，不做定向路由**。判定每条消息时，通用规则与全部已注册客户端规则同时生效，与基线行为严格等价。理由（specs 裁定）：混合会话实测普遍存在，WorkBuddy 的真实输入是「SR 框架块前置 + user_query 包裹真实指令」的复合形态（WorkBuddy 编排 Claude Code 会话），OMO 是装在 Claude Code 内的插件（同一会话 Claude Code 原生注入与 OMO 工具转写并存），若按识别结果只跑单一客户端规则，其他客户端的注入会漏判进视图污染证据。识别结果的消费是观测归因（提取通道参数化属后续演进方向，本期不交付），不承载判定正确性。
2. **前缀集合的分层拆分**。基线 injectPrefixesFactory 平面集合按形态归属拆到各客户端的 UserPrefixes，运行时有效黑名单 = 各客户端 UserPrefixes 并集 ∪ 通用层前缀 ∪ 参数页追加集；出厂态（追加集为空）下生效集与基线出厂集严格相等（等价性验收线，见 5.1）。assistant 收窄子集同法拆分（NonUserPrefixes 并集 == 基线 assistantPrefixesFactory，集合相等）。参数页追加语义（specs 裁定）：配置集只做追加不做替换，运维增补的前缀对所有客户端消息生效；删除配置条目只收回运维自己追加的条目（代码前缀并集不受配置影响，代码前缀的放开走代码变更发版），非 user 角色的收窄交逻辑保持基线语义（非 user 角色按「生效集与收窄子集的交集」判定）。
3. **内容语义通道的归属**。基线优先级 1 的内容语义白名单通道（SR 分流指纹/噪音/提取、command-args 提取、system 插话转述提取）逐条归属到贡献客户端（system-reminder 分流与 command 壳归 claude_code，SR 闭壳后 user_query 提取归 workbuddy），但通道执行顺序保持基线优先级链不变（提取类优先于丢弃类、指纹优先于噪音兜底），归属只影响代码组织与归属标注，不影响判定次序。
4. **判定链入口变薄**。classify.go 保留判定链编排（优先级次序、打断计数透出、区段状态机驱动），各优先级内的形态匹配委托通用层与客户端规则；classifyMsg 的函数签名与返回结构（classifyResult）不变，既有测试调用面稳定。

**注意事项**:
- 等价性是硬验收线：基线 5.1 全部表驱动用例（注入识别、重放拆分、WorkBuddy 家族、OMO 转写、碎片家族、compaction 对、指纹、插话、打断、粘贴判定等）在新结构下全绿，任何一条翻转即重构失败
- 前缀去重：不同客户端规则可能贡献相同前缀字面（如多个客户端都有 Note: 文件回显），并集时去重，避免运行时重复匹配开销
- 基线 2.2 InjectPrefixes 注释中的「同集合两视图」承诺在分层后收敛为「两视图」：基线形态清单（语义视图）与各客户端 UserPrefixes 并集（代码视图），两处集合相等由 5.1 注册表完备性测试守护；参数页出厂 seed 为空集（追加语义，见能力1 第 2 条），不再作为集合视图的第三源

#### 能力2: 特征抽取

> **[无变化]** 两段合成四块档案、prompt 组装、schema 校验、零输入/零叙述/零响应会话的 LLM 段行为与基线一致，详见基线文档 2.4 能力2。分层不进入 LLM 段：prompt、模板、统计参考块均不变。

#### 能力3: 档案落库

> [修改] 新增 client 列写入，其余幂等规则（success 即跳过、failed 翻转、skipped 终态、并发防御双通道、元数据复用）与基线一致。

**描述**: 三态落库行新增 client 列（探测结果在 prepare 阶段与裁剪同步产出，随行写入）。client 列对幂等判定无参与：既有 success/skipped 行复用照旧（复用行不重探测，client 回传既有行值）；failed 行翻转时 client 随新探测结果覆盖（探测是纯函数，同一 Detail 结果确定，覆盖值恒等）。残留 failed 行终态化为 skipped（session_not_found）时元数据列复用既有行原值，client 同随元数据复用原值（上游已无会话，不重探测）。detail_invalid 跳过行未经探测（判定在 prepare 之前短路，无消息可探测），client 落空串（值域七值之外的显式例外，观测按 client 聚合时空串行并入 detail_invalid 口径单独看）。

- client 列对 T5 消费是新增可用维度（按客户端拆 status 分布做人群签名识别），不改变既有 C01-C13 约束语义

#### 能力4: 短会话过滤

> **[无变化]** 判定规则（唯一权威定义见基线 2.4 能力4）、真实用户消息判定口径、排除项清单、人群签名披露与基线一致。过滤判据全部取裁剪结果，不感知客户端分层与识别结果。

#### 能力5: 指令脱敏

> **[无变化]** 正则集、占位符、已知盲区（带空格目录、版本号误杀面、捕获组风险）与基线一致。脱敏与客户端无关：敏感串形态不随客户端变化，全局单套正则，不按客户端拆分。

#### 能力6: 批量抽取编排入口

> **[无变化]** ExtractByKey 签名、拉详情错误分流、LLM 段错误分流、任务 handler 行为与基线一致。探测在 doExtract 内部执行，对编排入口透明。

#### 能力7: 客户端签名探测

**描述**: 逐会话对 Detail.Messages 跑全部已注册客户端的 DetectFeatures 计分，输出主客户端标识。设计要点：

1. **签名特征来源**：各客户端规则的专属强特征（基线实测形态的直接映射），如 workbuddy 的 `<user_query>`、`data-role="team-context"`、`data-role="user-context"` 前缀；omo 的 [SYSTEM DIRECTIVE:、OMO_INTERNAL_INITIATOR 尾标记、工具名加空格打头转写；automation 的提示词碎片家族前缀与分钟级会话节奏（节奏不进逐会话探测，仅形态特征参与）；claude_code 的 system-reminder 开式、command 壳、The user sent a new message 插话 marker；opencode 的 # Environment 环境头、The user has asked you to 播种形态（该前缀黑名单刻意不收录的裁定保留，探测侧仅用作识别信号）
2. **计分与裁决**：逐消息命中 Once 类前缀全会话计一次、累计类逐条计分；总分最高者为主客户端。权重标定（specs 裁定）：专属强特征（该客户端独有形态）权重 2-3，共享形态（多客户端共有的通用前缀）权重 1，标定约束 mixed 阈值的量纲稳定。裁决规则：次高分 > 0 且最高分与次高分分差 < 2 返回 mixed（严格并列分差为 0，含于该条件；WorkBuddy 包 Claude Code 形态下两客户端均得高分，mixed 是正确输出而非失败）；次高点为零分时（仅一个客户端得分，即便最高分为 1、分差 1 < 2）判该客户端归属，不判 mixed（mixed 语义是多客户端并存，单客户端弱信号会话归该客户端，防按 client 聚合的观测被稀释）；全部零分返回 unknown
3. **识别不承载判定正确性**：并集执行下探测错误的代价仅是观测归因偏差（client 列值失真），裁剪与过滤行为不受影响，这是探测可以采用轻量启发式的前提

**接口定义**:
```go
// DetectClient 纯函数，见 2.3 输出定义。
func DetectClient(detail *conversationlog.SessionDetail) string
```

**调用示例**:
```go
client := DetectClient(detail)
slog.Debug("client detected", "client", client)  // client 同时随落库行写入
```

**注意事项**:
- 探测在 prepare 阶段与裁剪共享同一份 messages 遍历（实现上可并入 classifySequence 单趟产出，避免二次全量扫描；独立函数形态保证可测性）
- 签名特征集随客户端规则文件演进（新客户端注册时自带 DetectFeatures），探测能力与注册表同步扩展，无独立维护的特征清单
- 单会话 client=unknown 属正常态不记错误日志；占比抬升经 6.3 低严重度提示消费（unknown_client_ratio 观测线，见 6.2）

#### 能力8: 客户端规则注册表

**描述**: 规则挂载扩展点。每个客户端规则文件实现 ClientRules 接口，init 时 Register 注册；判定链与探测执行期经 AllClientRules 只读消费。目标结构：

```
extractor/
├── rules/
│   ├── registry.go        # Register/AllClientRules，注册表本体
│   ├── generic.go         # 通用层前缀与共享形态常量（role 兜底、打断、内嵌 SR 剥离、
│   │                      # transcript 区段等判定逻辑留 classify.go，归属以注释标注）
│   ├── claudecode.go      # Claude Code：前缀集与探测特征（SR 分流、command 壳、插话等
│   │                      # 通道归属以 classify.go 注释标注）
│   ├── opencode.go        # OpenCode：前缀集与探测特征（环境头、播种形态）
│   ├── workbuddy.go       # WorkBuddy：前缀集与探测特征（user_query、team/user-context）
│   ├── omo.go             # OMO 类插件：前缀集与探测特征（工具转写、SYSTEM DIRECTIVE）
│   └── automation.go      # 自动化客户端：前缀集与探测特征（碎片家族、# System、count）
├── detect.go              # DetectClient 计分裁决
├── classify.go            # 判定链编排（变薄，签名不变；通道归属注释标注贡献客户端）
└── config.go              # 常量与全局追加参数读取（前缀出厂集改为各客户端并集的组装器）
```

规则文件承载 ClientRules 四方法（前缀集 + 探测特征），判定链与内容语义通道的实现留在 classify.go 与 generic 通用层执行路径中，通道的客户端归属以注释标注（能力1 第 3 条：归属只影响代码组织与归属标注，不影响判定次序）。

新客户端接入步骤：新增 rules/<client>.go 实现接口（含前缀、签名特征、若有专属提取通道一并实现）→ Register 一行 → 补表驱动测试与探测用例。既有客户端文件零改动。

**接口定义**:
```go
// 见 2.2 配置项说明的 ClientRules/Register/AllClientRules 定义。
```

**注意事项**:
- 注册顺序即 AllClientRules 返回顺序（init 顺序按文件名稳定），并集执行对顺序不敏感（前缀集合可交换），探测计分对顺序也不敏感（各客户端独立累计）
- 客户端规则文件内前缀与基线平面集合的对应关系须在文件头注释标注归属来源（基线形态编号），保证三视图可追溯
- registry 无反注册与运行时变更：规则集随二进制固定，热调仍走参数页全局追加（能力1 注意事项）

## 3. 技术约束

### 3.1 性能要求

> [修改] 新增探测耗时一行，其余指标与基线一致。分层不引入额外遍历：并集前缀匹配与基线平面匹配同为逐前缀 HasPrefix，探测并入裁剪单趟。

| 指标 | 要求 | 说明 |

### 3.2 兼容性要求

> **[无变化]** 版本兼容（Go 1.25、P2_TECH_002 契约、P2_TECH_001 双协议、三库兼容）与上游数据兼容（注入形态演进、tool_use 元数据、中文 token_name、空详情、空 model_name 子请求、黑名单跨模型边界、分页重复页、中文乱码）与基线一致，详见基线文档 3.2。分层新增两条：

### 6.2 监控指标

> [修改] 四项指标（extract_fail_ratio、skip_ratio、inject_residual_ratio、extract_duration）定义与告警阈值不变，观测口径新增按 client 列拆分维度。拆分价值：skip_ratio 基线按人群拆分的回填要求（基线 6.2，碎片人群、旁路族群、会议整理占比时变）获得结构化的第一拆分轴，黑名单失效排查从「逐会话猜形态」收敛为「看某客户端前缀命中」。

| 指标名称 | 指标类型 | 说明 | 告警阈值 |
|---------|---------|------|---------|
| extract_fail_ratio | 比率 | 同基线，可按 client 拆分观测 | ≥ 10% 触发工作台告警 |
| skip_ratio | 比率 | 同基线，基线回填时须按 client 拆分（碎片人群集中落 automation、旁路族群落 workbuddy/omo 等结构性关联） | 无告警，仅观测 |
| inject_residual_ratio | 比率 | 同基线，按 client 拆分后某客户端连续抬升即精确指向该客户端规则失效 | 连续两周期抬升提示 |
| unknown_client_ratio | 比率（新增） | client=unknown 占比 | 单周期 ≥ 20% 提示评估新客户端接入（观测线，非阻断告警） |

### 6.3 告警规则

> [修改] 基线两告警（抽取失败率超阈、黑名单失效嫌疑）保留，新增一条：

|---------|---------|---------|---------|
| 未识别客户端占比抬升 | unknown_client_ratio ≥ 20% | 低 | 从上游抽样 unknown 会话识别新客户端形态，评估按 rules/<client>.go 接入或按通用层参数页前缀兜底 |

### 6.4 故障排查

> [修改] 基线三问题（档案质量骤降、大量误过滤、schema 连续失败）排查路径不变。分层带来的排查增强：问题1 与问题2 的「从上游拉一条实际详情识别新前缀」步骤，先按 client 列过滤定位会话所属客户端，再到对应 rules/<client>.go 增补（或参数页全局追加），归属可追溯。新增一条：

**问题4: 探测结果失真（client 列与实际客户端不符）**
- 现象: 某人群 client 值与其已知客户端工具不一致，或 unknown 占比异常
- 原因: 新客户端未注册且零特征命中，或混合会话分差裁决落 mixed 的口径被误读
- 解决: 探测只影响观测归因不影响判定（并集执行），失真无正确性代价；按 6.3 新客户端路径接入规则后自然收敛
